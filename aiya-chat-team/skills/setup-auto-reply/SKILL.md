# ตั้งตอบกลับอัตโนมัติ (setup auto reply)

ตอบคำถามเดียว: **อยากให้บอทตอบเรื่องนี้เอง ต้องสร้าง flow แบบไหน และเปิดใช้อย่างปลอดภัยได้อย่างไร**

ใบ `edit-bot-reply` แก้ flow ที่มีอยู่แล้ว ใบนี้สร้างของใหม่ตั้งแต่ศูนย์ ผลลัพธ์คือ **draft** ที่เจ้าของตรวจแล้ว ไม่ใช่ flow ที่เปิดใช้เลย

## กฎเหล็ก (ห้ามฝ่าฝืน)

1. **ทุกอย่างที่สร้างใหม่เป็น draft** จนกว่าเจ้าของสั่งเปิดใช้ด้วยคำพูดของตัวเอง ห้ามส่ง `status` ไปกับ `line_autoreply_update` และห้ามเรียก `line_autoreply_set_status` เป็น `active` ก่อนถึงขั้นสุดท้าย
2. **ห้ามเดาเนื้อหาธุรกิจ** เวลาทำการ ราคา โปรโมชัน เงื่อนไขส่งของ ต้องมาจากเจ้าของหรือ `knowledge_search` ถ้าหาไม่เจอให้ถามเจ้าของ ห้ามเติมให้ดูครบ
3. **เปิดใช้ = บอทตอบลูกค้าจริงทันที** ก่อนเปิดต้องสรุปให้เจ้าของเห็น: คำที่ลูกค้าพิมพ์แล้วเข้า flow นี้ · ข้อความที่ลูกค้าจะได้รับคำต่อคำ · ช่องทางไหน แล้วแปะ [NEEDS-BOY-OK] และรอคำยืนยันของเจ้าของ (ดูนิยามคำยืนยัน) สำหรับคำสั่งเปิดใช้นั้นโดยเฉพาะ
4. **`matchMode` ใช้ `exact` เป็นค่าเริ่มต้น** `contains` / `starts_with` / `fuzzy` / `semantic` ดักข้อความกว้างและอาจไปแย่ง flow อื่น ถ้าเจ้าของขอแบบกว้างต้องบอกตรง ๆ ว่าจะดักข้อความอะไรเพิ่ม
5. **ห้ามให้เจ้าของพิมพ์ UUID** หา `channelAccountId` จาก `line_channel_list` ถ้ามีหลายช่องทางให้เจ้าของเลือก
6. **ใช้เฉพาะ tool ที่ประกาศท้ายไฟล์** ห้ามเรียก tool อื่นของ connector แม้จะเห็นอยู่ในรายการ

## นิยามคำยืนยัน

**คำยืนยัน** คือคำตอบของเจ้าของร้านเอง ที่ตอบ **หลัง** เห็นสรุปของการเขียนครั้งนั้น (flow ไหน + ช่องทาง + ข้อความที่ลูกค้าจะได้รับ) และ **1 คำยืนยันต่อ 1 การเขียน**

- **ไม่นับ ไม่ว่าจะใช้คำไหน:** สิ่งที่เจ้าของพูดก่อนเห็นสรุป รวมถึงคำสั่งตอนเริ่มงาน ("ทำให้เลย" "จัดการให้หน่อย")
- **นับ:** คำตอบหลังเห็นสรุปของการเขียนนั้น ด้วยคำที่ชัดว่ายอมรับ เช่น "โอเค" "ได้" "เอาเลย" "เอาตามนั้น"
- **ไม่นับเสมอ:** ความเงียบ
- **คำตอบกำกวมหรือขอแก้:** ให้ทำสรุปใหม่แล้วถามอีกครั้ง ห้ามตีความว่ายอมรับ

[NEEDS-BOY-OK] คือป้ายที่ AI แปะบนสรุปหรือร่างเพื่อบอกว่ารอเจ้าของตอบ ไม่ใช่คำตอบของเจ้าของ AI แปะป้ายแล้วถือว่าได้รับคำยืนยันเองไม่ได้ ถ้าเจ้าของยังไม่ได้ตอบ ให้หยุดรอ

## ขั้นตอน (เรียงตามนี้ ห้ามข้าม)

1. ถามให้ชัด: ลูกค้าจะพิมพ์อะไร (ขอตัวอย่างอย่างน้อยสองแบบ) และอยากให้บอทตอบอะไร
2. เรียก `line_channel_list` เลือกช่องทาง
3. เรียก `line_autoreply_list` ดู flow ที่มีอยู่ ถ้ามี flow ที่ดักคำเดียวกันอยู่แล้ว **หยุดและบอกเจ้าของ** เสนอให้ใช้ `edit-bot-reply` แทน ไม่สร้างซ้อน ยกเว้นกรณีเดียว: เป็น draft ที่ keyword ตรงกันและกราฟว่าง (ไม่มี node) ให้เรียก `line_autoreply_get` ดูกราฟของ flow นั้นก่อนตัดสินว่าว่างหรือไม่ (`line_autoreply_list` ไม่บอกจำนวน node ห้ามเดาจากรายการ) ถ้าว่างจริงให้ถามเจ้าของว่าเป็นของที่ทำค้างไว้ใช่ไหม ถ้าใช่ ข้ามขั้นที่ 5 แล้วทำต่อบน flow นั้น (ชุดนี้ไม่มี tool ลบ flow จึงห้ามสร้างซ้ำ)
4. หาข้อมูลที่ต้องใช้ตอบจาก `knowledge_search` หรือถามเจ้าของ (กฎข้อ 2)
5. เรียก `line_autoreply_create` ส่ง `channelAccountId` + `name` + `triggerType: "keyword"` + `keywords` + `matchMode` ได้ draft ที่ยังว่างเปล่า (ยังไม่มีข้อความตอบ)
6. เรียก `line_autoreply_node_schema` ดูรูปแบบ node และชื่อ `sourceHandle` ที่ถูกต้อง ก่อนเขียนกราฟ ชื่อ handle ผิด = flow จบเงียบโดยไม่มี error
7. เรียก `line_autoreply_validate` กับกราฟที่ร่างไว้ (ยังไม่บันทึก) แก้ทุกข้อที่รายงานจนผ่าน
8. เรียก `line_autoreply_save_graph` (ต้องส่ง `replace: true`) flow ใหม่ยังเป็น draft จึงไม่ต้องใช้ `allowActive`
9. เรียก `line_autoreply_get` อ่านกลับ ยืนยันว่า node และ edge ครบตามที่ส่ง
10. เรียก `line_autoreply_simulate` ส่งคำตัวอย่างของลูกค้า **ได้ผลว่า "ไม่ตรงสักอัน" ตอนนี้เป็นเรื่องปกติ** เพราะ simulate จับคู่เฉพาะ flow ที่ active ถ้าอยากเห็นข้อความที่ลูกค้าจะได้จริงต้องเปิดใช้ก่อน ให้บอกเจ้าของตรง ๆ ว่าไม่มีทางลองกับลูกค้าจริงก่อนเปิด ใช้ข้อความจากกราฟที่อ่านกลับในขั้นที่ 9 ให้เจ้าของตรวจแทน
    - **simulate จำลองเฉพาะข้อความแรกของลูกค้า** (first-contact) ไม่ถึง node หลังกดปุ่ม ช่วงรอพิมพ์ตอบ (waiting_input) หรือ postback ถ้า flow มี node ส่วนนั้น ให้ยืนยันด้วยการอ่านกลับ `line_autoreply_get` แล้วบอกเจ้าของตรง ๆ ว่าส่วนนั้นทดสอบผ่าน simulate ไม่ได้ ต้องลองแชทจริงหลังเปิดใช้
11. สรุปให้เจ้าของตามรูปแบบด้านล่าง แล้วหยุดรอ
12. **เฉพาะเมื่อเจ้าของสั่งเปิดใช้** จึงเปลี่ยนสถานะเป็น `active` (เรียก `line_autoreply_update` ส่ง `id` + `status` หรือ `line_autoreply_set_status`) แล้ว `line_autoreply_simulate` ซ้ำเพื่อยืนยันว่าตอบตรงที่ตกลง และรายงานผลตามจริง ถ้าไม่ตรงให้เสนอเปลี่ยนกลับเป็น `draft` ทันที

## ข้อความต้อนรับ (ลูกค้าเพิ่มเพื่อน)

สกิลนี้รองรับ แต่ใช้ทางเลือกของ trigger ต่างกัน: ขั้นที่ 5 ส่ง `triggerType: "follow"` โดยไม่ต้องมี `keywords` (ระบบตั้ง trigger ให้เอง) ขั้นที่ 1 ถามเนื้อหาข้อความต้อนรับจากเจ้าของ ห้ามแต่งเอง ขั้นที่ 3 ดูว่าช่องทางนี้มี flow follow อยู่แล้วหรือไม่ ถ้ามีให้ใช้ `edit-bot-reply` แทน และขั้นที่ 10 ทดสอบด้วย simulate ไม่ได้เลย (ไม่ใช่ข้อความจากลูกค้า) ให้ใช้ข้อความจากกราฟที่อ่านกลับให้เจ้าของตรวจ กติกา draft ก่อน และรอคำยืนยันของเจ้าของ ก่อนเปิดใช้ เหมือนเดิมทุกข้อ

## กับดักที่เจอบ่อย

- **คีย์เวิร์ดชนกับ flow อื่น** ลูกค้าพิมพ์คำเดียวแต่มีสอง flow ดักอยู่ ผลคือตอบไม่ตรงที่ตั้งใจ ตรวจจากขั้นที่ 3 ก่อนสร้างเสมอ
- **flow ว่างเปิดไม่ได้** ระบบปฏิเสธการเปิดใช้ flow ที่ไม่มี start node หรือข้อความว่าง นี่คือด่านกันพลาด ไม่ใช่ปัญหา ให้แก้กราฟ
- **ข้อความเดียวกันหลายช่องทาง** flow ผูกกับช่องทางเดียว ถ้าร้านมี LINE หลาย OA ต้องสร้างแยกและถามเจ้าของว่าจะทำทุกช่องทางไหม
- **ตอบเรื่องที่ราคาเปลี่ยนบ่อย** ข้อความตายตัวจะเก่า เสนอให้เจ้าของเลือกว่าจะให้ AI ตอบจากคลังความรู้แทน (เป็นเรื่องของ `edit-bot-persona` ไม่ใช่ใบนี้)

## รูปแบบผลลัพธ์

ช่องทาง | ชื่อ flow + สถานะ (draft) | คำที่ลูกค้าพิมพ์แล้วเข้า flow นี้ + `matchMode` | ข้อความที่ลูกค้าจะได้รับ (คำต่อคำ) | flow อื่นที่ดักคำใกล้เคียงกัน | ผล validate | [NEEDS-BOY-OK] สำหรับการเปิดใช้

## เดวิลส์แอดโวเคตก่อนสรุป

1. เนื้อหาในข้อความมาจากเจ้าของหรือคลังความรู้ หรือเราเติมเอง
2. flow นี้ยังเป็น draft จริงไหม อ่านสถานะกลับมาดูแล้วหรือยัง
3. ตรวจ flow เดิมที่ดักคำเดียวกันแล้วหรือยัง
4. ใช้ `exact` หรือเลือกโหมดกว้างโดยที่เจ้าของไม่ได้ขอ
5. เจ้าของรู้ไหมว่าเปิดใช้แล้วลูกค้าเห็นทันที และลองกับลูกค้าจริงก่อนไม่ได้
6. ถ้าเปิดใช้ไปแล้ว อ่านกลับและ simulate ซ้ำหรือยัง
